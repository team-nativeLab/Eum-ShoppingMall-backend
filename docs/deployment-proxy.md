# 운영 프록시 배포 점검

애플리케이션은 프록시 뒤에서 실행해야 합니다. 저장소에는 현재 특정 클라우드나 운영 프록시 설정이 없으므로, 아래 값은 실제 배포 환경의 주소와 방화벽 규칙에 맞춰 적용합니다.

## 애플리케이션 환경 변수

- `TRUSTED_PROXY_CIDRS`: 전달 헤더를 신뢰할 프록시의 정확한 CIDR 목록. 여러 대역은 쉼표로 구분합니다. 예: `10.20.1.0/24,2001:db8:1234::/64`. 실제 프록시 대역으로 교체하고 `0.0.0.0/0`, `::/0` 또는 모든 사설망을 넣지 않습니다.
- `REFRESH_COOKIE_SAME_SITE`: 기본값은 `Strict`입니다. 웹 프론트와 API가 서로 다른 사이트일 때만 `None`으로 바꾸고, HTTPS와 `Secure` 쿠키를 유지합니다. `None`과 `Secure=false` 조합은 애플리케이션 시작 시 거부됩니다.
- `CORS_ALLOWED_ORIGINS`: 쿠키 자격 증명을 쓰는 CORS 허용 프론트엔드 주소를 정확히 지정합니다. 와일드카드 대신 실제 origin 목록을 사용합니다. Refresh/logout 요청은 이 목록에 없는 `Origin`에서 오면 거부합니다.
- `CORS_ALLOWED_ORIGINS`: 쿠키 자격 증명을 쓰는 CORS 허용 프론트엔드 주소를 정확히 지정합니다. 와일드카드 대신 실제 origin 목록을 사용합니다.
- Redis 연결 환경 변수는 공유 가능한 운영 Redis를 가리켜야 합니다. 로컬 단일 인스턴스용 주소를 운영에 그대로 쓰지 않습니다.

## 네트워크와 프록시

- 인터넷에서 애플리케이션 포트로 직접 들어오는 연결을 막고, 프록시 보안 그룹/서브넷에서 오는 연결만 허용합니다. 애플리케이션이 프록시와 같은 사설망에 있다면 방화벽 규칙도 해당 프록시 CIDR로 제한합니다.
- 프록시는 클라이언트가 보낸 `X-Forwarded-For`를 그대로 이어 붙이지 말고, 연결된 실제 클라이언트 IP로 덮어써야 합니다. `X-Forwarded-Proto`와 `Host`도 프록시가 설정합니다.
- HTTPS 종료 지점에서 HTTP를 HTTPS로 리다이렉트하고 HSTS를 적용합니다.
- 프록시 본문 제한은 최소 10 MB로 설정합니다. 애플리케이션은 이미지 파일 5 MB, 멀티파트 요청 6 MB까지 받습니다.
- 결제 응답을 기다리는 프록시 제한은 60초 이상으로 둡니다. 현재 애플리케이션의 PG 응답 대기시간은 10초입니다.
- 로드밸런서 헬스체크는 `GET /actuator/health/readiness`를 사용합니다. Readiness에는 Redis 상태도 포함됩니다. Redis는 토큰 검증과 공유 요청 제한에 필요하기 때문입니다.
- 관리자 API를 사무실 IP로 제한하려면 고정된 사무실 CIDR을 확인한 뒤 프록시 방화벽에서 별도로 적용합니다. 사무실 대역이 없으면 VPN/관리 네트워크 정책을 정해야 합니다.

## 배포 후 확인

1. 프록시를 통과한 요청 두 개에서 서로 다른 클라이언트 IP가 애플리케이션에 전달되고, 각 IP의 요청 제한이 독립적인지 확인합니다.
2. 신뢰 CIDR 밖에서 위조한 `X-Forwarded-For`가 클라이언트 IP를 바꾸지 못하는지 확인합니다.
3. 애플리케이션 포트가 프록시 외부에서 접근되지 않는지 네트워크 규칙을 확인합니다.
4. 5 MB 업로드, 토큰 재발급 쿠키, readiness 응답을 실제 운영 도메인에서 확인합니다.

운영 프록시 종류, 실제 CIDR, 방화벽 및 HTTPS 설정은 이 저장소만으로 확정할 수 없으므로 배포 대상에서 적용하고 점검 결과를 기록해야 합니다.
